セキュリティ設計（多層防御）

本アプリは WinMerge が生成した「信頼できない HTML ファイル」をブラウザ内で直接レンダリングするため、 XSS 対策が最重要の設計要素です。html-processor.js を中心に、以下の防御を積み重ねています。

層対策実装箇所
1mutation XSS 対策：<style>タグ内のコメント記法（<!-- -->）を事前に除去_stripStyleComments()
2DOMPurify によるホワイトリスト方式のサニタイズ（script/iframe等の危険タグ、on*属性等を除去）CONFIG.ALLOWED_TAGS / ALLOWED_ATTR
3style属性内の危険パターン検査（javascript: / expression() / @import / binding: 等）uponSanitizeAttributeフック
4<style>タグ全体に対する同様のパターン検査。検出時はブロック単位で丸ごと拒否（fail-closed）_sanitizeStyleText()
5レポートのCSSを #viewer 配下にスコープ化。html/body/:rootが#viewer自身を直接指してしまうケースでは、display/visibility等「表示を消し去るプロパティ」だけを追加で除去する_scopeCss()
さらにブラウザ側の防御として、index.htmlのCSP（Content-Security-Policy）で script-srcを自ドメインとFont AwesomeのCDNのみに制限し、外部への不要な接続や インラインスクリプトの実行を防いでいます。DOMPurify本体もCDNではなくjs/vendor/に ベンダリングしているため、外部スクリプト読み込みへの依存自体を減らしています。

加えて、DOMを構築する全モジュールで「ユーザー由来のテキストはtextContentのみで挿入し、 innerHTMLには動的な値を渡さない」という方針が徹底されています。これはDOMPurifyの サニタイズが万一漏れた場合の「もう一段の砦」として機能します。

⚠ CSSスコープエスケープの脆弱性修正（実例）
過去に、悪意あるCSSでhtml, body { display: none }のようなルールを仕込むと、 スコープ化後に#viewer, #viewer { display: none }となり、ビューア表示領域そのものが 消し去られてしまう脆弱性が報告されました。_isViewerRootSelector()で 「コンビネータを介さず#viewer自身を指すセレクターか」を判定し、該当する場合のみ 表示制御系プロパティを除去する対策が現在の実装（上表の層5）です。

データフロー（ファイル処理）

ファイルが選択されてから差分表示までの処理ステップです。file-handler.js がオーケストレーターとして各モジュールを順に呼び出します。

ステップ処理内容担当モジュール進捗
readFileReader でファイルを読み込み・文字コード判定（UTF-8 / Shift-JIS）file-handler.js0〜20%
sanitizeHTML をサニタイズ（危険タグ・属性を除去）html-processor.js20〜40%
parseDOMParser で Document を生成し、<style>タグのCSSを #viewer 配下にインポートhtml-processor.js40〜50%
detect差分テーブルを抽出・複製し、右端バーを付与して viewer に挿入html-processor.js（内部で table-processor.js を利用）50〜70%
marker固定ヘッダー生成 → 差分ブロック検出 → ミニマップマーカーを左右ペインに生成・配置table-processor.js / diff-detector.js / block-marker-generator.js70〜90%
renderナビゲーションボタンを接続し、ツールヘッダーを非表示化file-handler.js90〜100%
ステップ名「detect」は差分テーブルの検出を指し、差分ブロックの検出 （DiffBlockDetector.detectBlocks()）は次の「marker」ステップの中で行われます。 ステップ名と実処理の対応が直感的でない箇所なので、コードを追う際は注意してください。

差分色定義（config.js）

差分色は config.js の DIFF_COLOR_MAP で一元管理しています。変更する場合はここだけ編集してください。

WinMerge のデフォルトカラースキーム（Default.ini）と一致しています。 WinMerge 内部は BGR 形式ですが、HTML レポート出力時に RGB に変換されるため RGB で定義しています。

ミニマップのマーカー色は style.css の CSS 変数（--minimap-color-*）で管理しています。差分色とは別系統です。

typelabel差分色（RGB）HEXミニマップ色左ペイン右ペイン
changed変更行rgb(239, 203, 5)#efcb05#FFD700✅✅
word変更行内差分rgb(241, 226, 173)#f1e2ad#FFD700✅✅
del削除・追加行rgb(255, 160, 160)#ffa0a0#C0C0C0✅❌
moved_from移動元rgb(255, 170, 130)#ffaa82#FFA500✅❌
moved_to移動先rgb(200, 129, 108)#c8816c#FFA500❌✅
separator区切り行rgb(192, 192, 192)#c0c0c0#C0C0C0✅✅
⚠ isNeutral() の閾値について
table-processor.js の isNeutral() は閾値 240 で白・薄グレーを中立色と判定します。 差分色を変更する場合は、すべての色のチャンネル最小値が 240 を超えないことを確認してください。

テスト構成

種別ディレクトリツール環境
ユニットテスト tests/*.test.js（モジュールごとにフラット配置、21ファイル） Vitest jsdom（仮想DOM）
統合テスト tests/integration/ Vitest + jsdom jsdom（複数モジュール連携）
E2E テスト tests/e2e/ Playwright Chromium（実ブラウザ）
テスト用データ tests/fixtures/ ― 実際のWinMergeレポート・悪意あるサンプルHTML等
tests/unit/・tests/dom/のようなディレクトリ分割は行っておらず、 対象モジュールと同じ粒度でテストファイルをフラットに並べる方針です （例: html-processor.js → tests/html-processor.test.js）。 同一モジュールでもカバレッジ補強用に*-extra.test.js / *-coverage.test.js のように分割されている場合があります。

デバッグ方法

URL に ?debug=true を付けるか、localhost / 127.0.0.1 で開くとデバッグモードが有効になります。

ブラウザコンソールで使用可能なデバッグ関数

デバッグモードでは window.WinMergeViewer に加えて、短縮エイリアス window.wmv と window.debug（wmv.debugと同じ）が公開されます。 

wmv.debug.showBlocks()      // 差分ブロック統計・一覧
wmv.debug.visualizeBlocks() // ブロックを色枠で視覚化
wmv.debug.blockMode()       // 現在のブロック数・currentDiffIndexを表示
wmv.debug.memoryStatus()    // メモリ使用量（performance.memory）
wmv.debug.appState()        // AppState の状態ダンプ
wmv.debug.all()             // memoryStatus・appState・blockModeをまとめて表示

// 上記はすべて debug.xxx() の形でも呼び出せる
debug.all()

CI/CD・デプロイ

⚠ 以前の運用からの変更点
かつては gh-pages ブランチへ git checkout でファイルを手動コピーして 公開する運用でしたが、現在は .github/workflows/deploy-pages.yml により main ブランチから直接・自動でGitHub Pagesへデプロイされる方式に置き換わっています。 gh-pages ブランチへの手動反映作業は不要です。

CI：.github/workflows/test.yml

mainへの push または main 宛のPull Requestのたびに、3つのジョブが並列実行されます。

ジョブ内容
unit-testnpm ci → Vitestでカバレッジ付き単体テストを実行。カバレッジレポートはArtifacts（30日保存）に保存
lintESLint（JS）とStylelint（CSS）で静的解析
e2e-testPlaywright（Chromium）で実ブラウザテストを実行。失敗時はスクリーンショットをArtifactsに保存

CD：.github/workflows/deploy-pages.yml

index.html / document.html / style.css / favicon.ico / js/** のいずれかが main に変更として入った時だけ発火します （workflow_dispatchでの手動実行も可能）。

  1. リポジトリをチェックアウト
  2. 公開に必要な静的ファイルだけを pages-dist/ に集める（node_modules・テストコード・設定ファイルは含めない）
  3. actions/upload-pages-artifact でアーティファクト化し、actions/deploy-pages で直接GitHub Pagesへデプロイ
concurrency 設定により、連続してpushがあった場合は古いデプロイを打ち切り最新のものだけを 反映するため、デプロイが競合して壊れることを防いでいます。

ローカルでの品質ゲート（コミット時）

CIより手前、git commit の瞬間にも品質チェックが仕込まれています。 package.json の lint-staged 設定と Husky の pre-commit フックにより、 コミットのたびにステージされたファイルだけ ESLint・Prettier（JS）や Stylelint・Prettier（CSS）が 自動実行されます。CIで初めて問題に気づくのではなく、コミットの時点で機械的に直せる問題（整形崩れ等）は 直してしまう「シフトレフト」の実践です。

全体の流れ

git commit（Husky/lint-staged でローカル整形・簡易チェック）
   ↓
git push（test.yml: unit-test / lint / e2e-test を並列実行）
   ↓
main への反映が対象ファイルを含む場合（deploy-pages.yml が発火）
   ↓
GitHub Pages へ自動デプロイ

依存関係の自動更新

.github/dependabot.yml により、npm依存パッケージの更新PRが週次で自動作成されます （同時オープンPR数は5件まで）。既知の脆弱性を含む古い依存を放置しないための仕組みです。
